# Namviek Python 项目开发约束规则

> 适用范围：本仓库所有前后端开发任务。AI 助手在执行任何代码变更前必须遵循以下约束。

---

## 1. 代码质量约束

### 1.1 语法与编译

- **零语法错误**：所有提交的代码必须无语法错误，前后端均需通过编译/类型检查。
  - 后端（Python/FastAPI）：`py_compile` 或 `mypy` 检查通过。
  - 前端（TypeScript/Next.js）：`tsc --noEmit` 类型检查通过。
- **类型安全**：前后端均要求严格的类型标注，禁止使用 `any`（除极少数兼容层），后端使用 Pydantic 模型，前端使用 TypeScript 接口/类型。

### 1.2 无用代码清理

- **及时清理**：每次开发完成后，必须清理以下内容：
  - 未使用的 `import` 语句。
  - 未使用的变量、函数、组件。
  - 注释掉的无用代码块（调试用的 `console.log`、`print` 等）。
  - 废弃的文件和目录。
- **禁止遗留调试代码**：开发过程中的 `console.log`、`print()`、`debugger` 等调试语句在提交前必须移除。

### 1.3 代码风格

- 后端遵循 PEP 8，使用 `ruff format` 风格。
- 前端遵循项目 `.prettierrc` 配置。
- 函数/组件保持单一职责，单个文件不超过 300 行（超出则考虑拆分）。

---

## 2. API 响应格式一致性约束

### 2.1 后端响应格式

- FastAPI 后端对认证相关接口保持旧格式 `{ "status": 200, "data": {...} }`（兼容前端 `AuthResponse`）。
- 其他业务接口（组织、项目、任务等）返回扁平化对象或数组，**不包裹** `{ status, data }` 结构。
- 所有创建资源接口使用 `HTTP 201 Created` 状态码。

### 2.2 前端数据解包

- 前端所有 API 调用必须使用兼容模式解包：
  ```typescript
  const data = res.data?.data ?? res.data
  ```
- 禁止直接使用 `const { data } = res.data`（旧 NestJS 格式），除非明确确认该接口返回包裹格式。
- 状态码判断使用范围检查：`status < 200 || status >= 300`，禁止 `status !== 200`。

---

## 3. 功能测试约束

### 3.1 开发后自动测试

- 每次功能开发完成后，必须进行以下验证：
  1. **类型检查**：前端执行 `tsc --noEmit`，后端执行 `mypy` 或 `py_compile`。
  2. **单元测试**：后端执行 `pytest`，确保现有测试通过。
  3. **功能验证**：通过浏览器自动化或手动测试核心流程（登录、创建组织、进入工作台等）。
  4. **回归检查**：确认本次变更未破坏已有功能。

### 3.2 测试覆盖

- 后端新增 API 必须附带对应的 pytest 测试用例（正常流程 + 异常分支）。
- 前端新增组件/页面必须验证渲染无报错、交互正常。

### 3.3 浏览器自动化验证

- 对于涉及页面跳转、用户交互的功能，使用浏览器自动化工具验证：
  - 页面是否正确渲染。
  - 跳转是否到正确 URL。
  - 是否有控制台错误。
  - 加载状态是否正确结束（不卡在 "Fetching..." 等加载态）。

---

## 4. 性能约束

### 4.1 响应时间

- 后端 API 响应时间：
  - 普通查询接口 < 200ms。
  - 列表/聚合接口 < 500ms。
  - 超时阈值：单个请求不超过 30s。
- 前端页面加载：
  - 首屏加载（FCP）< 1.5s。
  - 页面跳转感知时间 < 1s。
  - 交互响应（点击反馈）< 200ms。

### 4.2 数据库查询优化

- 避免循环内执行数据库查询（N+1 问题）。
- 列表查询必须使用分页或限制返回数量。
- MongoDB 查询确保必要的索引覆盖。

### 4.3 前端渲染优化

- 避免不必要的重渲染，合理使用 `useMemo`、`useCallback`。
- 列表渲染使用 `key` 属性，避免使用 index 作为 key。
- 图片资源使用懒加载，禁止在首屏加载大量未使用资源。

---

## 5. 用户体验约束

### 5.1 加载状态

- 所有异步操作必须有加载反馈：
  - 按钮点击后显示 loading 状态。
  - 页面跳转时显示 "Redirecting..." 或骨架屏。
  - 数据加载时显示骨架屏或 Loading 占位符。
- 加载状态必须在操作完成后立即结束，禁止卡在永久加载态。

### 5.2 错误处理

- 所有用户可见的错误必须有友好的错误提示（使用 `messageError` 或 Toast 组件）。
- 禁止在界面上展示原始错误堆栈或技术性错误信息。
- 网络错误、超时、401/403 等场景必须有明确的用户引导（如"请重新登录"）。

### 5.3 表单交互

- 表单提交前必须进行前端校验。
- 校验失败时高亮错误字段并显示具体提示。
- 提交按钮在 loading 期间禁用，防止重复提交。

### 5.4 路由与导航

- 登录后自动跳转到目标页面或 `/organization`。
- 未登录访问受保护页面时跳转到 `/sign-in`。
- 页面跳转后状态正确重置，不残留旧页面的临时状态。

---

## 6. 安全约束

### 6.1 认证与授权

- 所有受保护接口必须验证 JWT 令牌。
- 前端请求拦截器自动附加 `Authorization` 和 `refreshtoken` 头。
- Token 过期时自动刷新或引导重新登录。

### 6.2 数据安全

- 密码使用 `pwdlib` 哈希存储，禁止明文存储。
- JWT 密钥从环境变量读取，禁止硬编码。
- 敏感信息（密钥、数据库连接串）仅放在 `.env` 文件，不提交到版本库。

### 6.3 输入验证

- 后端所有接口入参使用 Pydantic 模型校验。
- 前端表单输入进行格式校验后再提交。
- 防止 XSS：用户输入渲染前进行转义。

---

## 7. 架构一致性约束

### 7.1 后端分层

- 严格遵循 Model → Schema → Repository → Service → Route 分层架构。
- 禁止在路由层直接操作数据库。
- 禁止在 Service 层直接使用 `Response` 对象。
- 依赖注入通过 `app/api/dependencies.py` 统一管理。

### 7.2 前端模块化

- 页面组件放在 `app/` 目录（Next.js App Router）。
- 可复用组件放在 `components/` 或 `_components/`。
- 业务逻辑封装在 hooks 中，禁止在组件内直接写复杂业务逻辑。
- 状态管理使用 Zustand，Context API 仅用于跨页面共享。

### 7.3 Prisma 类型兼容

- 前端使用 `types/prisma-client.d.ts` 类型声明文件替代 `@prisma/client`。
- 运行时枚举值通过 `lib/prisma-shim.js` 提供。
- 禁止直接安装或使用实际的 `@prisma/client` 包。

---

## 8. 提交规范约束

### 8.1 变更前

- 修改代码前必须先阅读目标文件，理解现有逻辑。
- 禁止在不了解上下文的情况下进行大段覆盖式重写。
- 优先使用最小化编辑（`Edit`），避免不必要的文件创建。

### 8.2 变更后

- 确认无语法错误、类型错误。
- 确认无用代码已清理。
- 确认功能测试通过。
- 确认不影响已有功能（回归测试）。

### 8.3 变更范围

- 仅修改与任务直接相关的文件。
- 禁止顺手重构无关代码（除非用户明确要求）。
- 禁止添加用户未要求的功能、配置或文档。

---

## 9. 环境与启动约束

### 9.1 服务端口

- 后端 FastAPI：`http://localhost:8000`
- 前端 Next.js：`http://localhost:3000`
- MongoDB：通过 Docker Compose 启动，副本集模式。

### 9.2 环境变量

- 后端配置文件：`backend/.env`
- 前端配置文件：`frontend/.env.local`
- `NEXT_PUBLIC_BE_GATEWAY=http://localhost:8000/`

### 9.3 依赖管理

- 后端使用 `uv` 管理依赖。
- 前端使用 `yarn` 管理依赖。
- 禁止混用 `npm` 和 `yarn`。

---

## 10. 问题排查约束

### 10.1 排查流程

1. **先读代码**：通过 Read/Grep/SearchCodebase 定位问题。
2. **再复现**：通过浏览器自动化或 API 调用复现问题。
3. **定位根因**：基于代码级证据定位，不猜测。
4. **最小修复**：只修改必要的代码，不扩大改动范围。
5. **验证修复**：通过实际操作验证修复有效。

### 10.2 禁止行为

- 禁止在未读取文件的情况下提出修改建议。
- 禁止在未验证的情况下声称"已修复"。
- 禁止用暴力重试掩盖问题根因。
- 禁止忽略控制台错误和警告。

---

## 违规处理

当 AI 助手的行为违反上述任一约束时，应立即停止当前操作，回退不必要的变更，并按约束规则重新执行。
